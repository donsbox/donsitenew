## Problem framing: more drafts do not complete the job

Turning one source into content for X and Xiaohongshu requires different structures, levels of detail and interaction patterns. A single generation step can leave strategy, editing, publishing preparation and review disconnected. The next project then starts without a usable record of earlier decisions.

RELAY organizes these activities around saved content assets rather than isolated chat responses. This product framing is an interpretation of the repository’s structure; no user-research study or measured effectiveness has been verified.

## Scope and product decisions

The generation workflow focuses on X and Xiaohongshu: retain a shared thesis, then adapt the output for each platform. Other platforms appear in types or interfaces, but that does not establish completed generation support.

Human judgment remains in strategy selection, editing and final-version selection. A Publishing Pack assembles final material and publishing guidance. It is a preparation artifact, not evidence of a connected automatic-posting system.

## Architecture: separate interaction, orchestration and artifacts

| Layer | Objects or responsibilities | Product rationale |
| --- | --- | --- |
| Workspace | Intake, Strategy, Output Studio, Publishing Pack, Review, Benchmark Library | Guide users through a task rather than a collection of prompts |
| Workflow | Parse input, create a brief, retrieve context, recommend strategy, create outputs and a pack | Make dependencies, progress and failure states explicit |
| Domain assets | ContentProject, Artifact, WorkflowRun | Connect projects, generated results and run records |
| Adapters | LocalStorage, playbooks, model gateway | Provide replaceable persistence and generation boundaries for a prototype |

Artifact types cover briefs, strategies, platform plans, outputs, publishing packs, reviews and memory. Fields include a project ID, optional run ID, version and timestamps. One result can therefore become the next step’s input instead of disappearing into a conversation.

## Workflow design: place judgment inside the process

1. **Intake and analysis.** Source material, goals and platforms feed a brief, playbook retrieval and strategy recommendations. WorkflowRun tracks individual steps and records the active step on failure.
2. **Strategy and planning.** Users can select a strategy, while the code also permits a recommended-strategy fallback. Explicit human strategy confirmation is therefore not enforced in every path.
3. **Platform output and editing.** Writers create platform-specific content blocks. Edits and final selections are saved as new artifacts.
4. **Publishing preparation.** The pack builder assembles final assets and guidance from the saved outputs.
5. **Review and reuse.** Manually entered performance data updates rule-based user memory, which is read by later strategy and writing steps.

The agents are responsibility-specific modules. Their presence does not establish autonomous planning, automatic account operation or proven multi-agent performance.

## Delivered artifacts and implementation boundaries

The earlier MVP_STATUS document still lists Performance Review, User Memory and a real-provider gateway as unimplemented. The inspected snapshot contains those modules and page wiring. This case follows current source and classifies them as code present, without treating either source or documentation as a runtime acceptance result.

The gateway defaults to mock generation and falls back when configuration is incomplete or requests fail. The compatible provider contains timeout handling and limited request-format retry. Brief and platform-output paths include shape checks and rule-based fallback. This establishes an integration path, not successful production calls, exhaustive validation or consistently visible fallback states.

Persistence uses browser LocalStorage. Benchmarks come from seed and custom playbooks, not verified live trend ingestion. Memory is assembled from manually supplied data and rules; it is neither model training nor a multi-user isolation mechanism.

## Validation plan and product measures

First validate the complete path from intake through editing, refresh recovery, publishing preparation and review. Then test a real provider, failure recovery and visible fallback behavior. Production readiness also requires server-side credential handling, authentication and data isolation; browser-side provider configuration does not establish that readiness.

The status document proposes weekly actually published assets as a north-star measure. Publication rate after generation, time to publishing pack and edit volume would help evaluate usefulness. These are **proposed measurements**, not reported growth results.
